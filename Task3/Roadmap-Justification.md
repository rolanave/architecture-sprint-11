# **Аргументация роадмапа**

## Цели Бизнеса:
1. Запуск портала самообслуживания
2. Обеспечить независимое развитие подразделений
3. Поддержать качество медицинских и финансовых сервисов

## Ожидаемые сроки реализации:

|Период| Задачи |
|--|----------------------------------|
|Q1| <ol><li>Архитектурное решение по трансформации сформировано и согласовано.</li><li>Границы доменов определены, а ключевые связи между ними описаны.</li><li>В доменах запланированы конкретные проекты по развитию «витрины данных».</li></ol>|
|Q2-4|<ol><li>Реализован портал самообслуживания.</li><li>Бизнес-пользователи в доменах могут работать с данными в рамках новой архитектуры.</li></ol>|

## Анализ Требований:
### R1. Запуск портала самообслуживания

#### Функциональные требования:
 Портал самообслуживания предполагает, что бизнес-пользователь может
- Войти в систему (Идентификация, Аутентификация и Авторизация)
- Настроить одну или несколько витрин данных из тех, что ему доступны
- Получить сгенерированный отчет в рамках созданной ранее витрине данных

#### Нефункциональные требования:
- Портал не должен влиять на производительность и работоспособность текущих медицинских и финансовых сервисов
- Портал должен поддерживать большое количество пользователей и иметь возможность масштабирования при росте нагрузки
- Портал должен поддерживать высокий уровень доступности
- Портал не должен иметь длительное время отклика

#### Предварительные шаги по реализации портала:
1. Команда аналитиков - разработка архитектурного решения и детального дизайна для портала - Q1
2. Команда инфраструктуры - подготовка инфраструктуры для разработки портала (+ пайплайн CI/CD) - Q1
3. Команда разработчиков - разработка портала, смоук тестирования - Q2-Q3
4. Команда тестирования и команда разработчиков - тестирование портала и ввод в эксплуатацию - Q4 

### R2. Обеспечить независимое развитие подразделений

#### Решение:
Предлагается использовать доменный подход в рамках Data Mesh для независимого внедрения и развития новых подразделений

#### Предположение:
Существующий DWH может быть использован для хранения данных (и метаданных) новых подразделений и отчетов. 
Если DWH будет становиться узким местом, то возможно вынесение хранение данных отдельных подразделений или отчетов (шардирование) в новый DWH. 

#### Функциональные требования 
- Разработка каталога витрин, в рамках которого каждый домен/подразделение мог бы хранить информацию о нужных ему витринах данных
- Разработка каталога данных, в рамках которого каждое подразделение сможет описать:
  - структуру входных данных (какие данные и как должны приходить и как трансформироваться при загрузке в хранилище)
  - структуру данных доступных для внешних сервисов (API для других доменов) 
  - какие данные доступны для построения отчетов и какие права нужны для этих данных
- Разработка взамодействия с оркестратором данных (Appach Nifi или AirFlow) по
  - ETL данных из источника данных согласно каталогу данных
  - трансформации и выгрузке (в портал) загруженных данных для генерации отчета согласно каталогу витрин данных

#### Нефункциональные требования:
- Работа каталога витрин, каталога данных и оркестратора данных не должна снижать производительность основных сервисов (медицина/финансы)
- Каталоги и оркестратор данных должны поддерживать большие потоки данных и иметь возможность масштабирования при росте нагрузки
- Потоки данных должны быть изолированы между доменами
- Каталоги и оркестратор данных должны поддерживать высокий уровень доступности
 
#### Предварительные шаги по реализации:
5. Команда аналитиков - разработка архитектурного решения и детального дизайна для трансформации (определение доменов и прочее) - Q1
6. Команда инфраструктуры - подготовка инфраструктуры для разработки каталогов и оркестратора (+ пайплайн CI/CD) - Q1
7. Команда инфраструктуры - разворачивание оркестратора данных - Q2
8. Команда разработчиков - разработка каталогов, смоук тестирования - Q2
9. Команда тестирования и команда разработчиков (поддержки) - Интеграционное тестирование решения (каталоги, оркестрация) - Q3
10. Команда тестирования и команда разработчиков (поддержки) - Тестирование решения и ввод в эксплуатацию - Q4 

### R3. Поддержать качество медицинских и финансовых сервисов

#### Предположения
- В рамках ближайшей перспективы предлагается оставить легаси решение для медицинского домена, чтобы снизить импакт от произведенных изменений. 
- В дальнейшем возможен переход на общую доменную инфраструктуру для  работы с данными медицинский сервисов  с целью повысить масштабируемость, надежность и унифицированность решения (для этого предлагается реализовать MVP перед принятием решения о трансформации).

#### Предварительные шаги по реализации:
11. Команда разработчиков и инфраструктуры - работа над техдолгом и поддержке по существующему решению - Q1-Q4
12. Команда инноваций - разработка MVP для интеграции медицинского сервиса в новую инфраструктуру - Q3-Q4
